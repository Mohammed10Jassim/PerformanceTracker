# 03 — Database Schema

## 1. ERD summary

- `BaseEntity` columns (`id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `is_active`)
  are inherited by **all 14 tables**.
- Every foreign key is `NOT NULL` and uses `FetchType.LAZY`.
- Deletions are never performed: data is toggled via `is_active`.
- 13 identity sequences (`*_id_seq`) exist; one extra sequence is **manual**:
  `department_code_seq` (used to generate `department_code` values).

The data chain is:

```
projects (1) ─< project_departments (M) ─ department (1)
                      │
                      └─ project_kras (M)
                            │
                            └─ project_kpas (M)
                                  │
                                  └─ project_kpa_employees (M) ─ employee (1)
                                            │
                                            └─ project_kpa_tasks (M)

employees (M) ─< employee_department_designations (join) >─ department_designations (M)
department_designations (M) ─ department (1), ─ designation (1)

users (1:1) employee (1)
users (M) ─< user_roles (join) >─ roles (M)
```

## 8. Notes and caveats

- **No DB UK on `projects.project_name`.** The service checks `existsByProjectNameIgnoreCase` on
  create/update; uniqueness is enforced at application level only.
- **`employee_code` has no auto-generation.** The API expects the caller to supply it and enforces
  uniqueness.
- **Join tables with no surrogate `id`:** `employee_department_designations` and `user_roles` use a
  composite key (implicit). The others have their own `id` identity column.
- **`department_code` generation is external to Hibernate.** You **must** create
  `department_code_seq` before the first department insert, or the native `nextval` will fail.
- **Soft-delete everywhere.** There are no `ON DELETE CASCADE` rules that remove children; children
  remain when parents are deactivated. Business logic prevents activating a child when its parent
  is inactive (see [07](./07-business-rules.md)).
- **Precision cap:** `completion_percentage` is `NUMERIC(5,2)` (max `999.99`). The computed values
  are always 0–100, so this is safe today.
- **Enum storage:** `ProjectStatus` and `TaskStatus` are stored as `VARCHAR` (not as ordinal). This
  is correct and explicit via `@Enumerated(EnumType.STRING)`.
